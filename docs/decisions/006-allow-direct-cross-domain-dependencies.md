# Allow Direct Cross-Domain Dependencies

## Context

현재 프로젝트는 하나의 애플리케이션과 데이터베이스로 배포되는 작은 계층형 모놀리스다. 패키지는 사용자, 상품, 장바구니, 주문, 결제 도메인으로 구분되어 있지만, 각 도메인을 독립 모듈처럼 강하게 격리하지는 않는다.

도메인을 넘는 흐름에서는 다른 도메인의 서비스, 저장소, 엔티티 같은 구체 타입을 직접 사용할 수 있다. 예를 들어 `PaymentService`는 주문과 주문 항목 저장소에 직접 의존하고, 결제 완료 시 주문 항목이 참조하는 `Product` 엔티티의 `decreaseStock()`을 호출한다.

이러한 의존을 공개 인터페이스, 애플리케이션 이벤트, 별도 포트와 어댑터로 감싸면 도메인 경계를 더 명시적으로 만들 수 있다. 그러나 현재 규모와 변경 빈도에서는 경계 유지에 필요한 추상화와 간접 호출이 얻는 이점보다 구현 및 탐색 비용을 더 크게 만들 수 있다.

## Options

### 도메인 간 직접 의존 허용

장점:

- 하나의 트랜잭션으로 여러 도메인의 상태를 변경하는 흐름을 단순하게 구현할 수 있다.
- 인터페이스, 이벤트, 변환 객체 같은 추가 계층이 없어 코드 흐름을 쉽게 추적할 수 있다.
- 현재 프로젝트 규모에 비해 과도한 추상화를 피할 수 있다.

단점:

- 한 도메인의 내부 구조 변경이 다른 도메인에 영향을 줄 수 있다.
- 의존 방향과 도메인 소유권이 코드만으로 불명확해질 수 있다.
- 프로젝트가 커지면 도메인의 독립적인 변경, 테스트, 분리가 어려워질 수 있다.

### 공개 인터페이스 또는 포트로 도메인 경계 강화

장점:

- 각 도메인이 외부에 제공하는 기능과 의존 방향이 명확해진다.
- 다른 도메인의 저장소와 엔티티 내부 구조에 대한 결합을 줄일 수 있다.
- 향후 모듈 분리나 외부 시스템 연동에 유리하다.

단점:

- 현재 규모에서는 인터페이스와 구현체가 일대일로 대응하는 형식적인 추상화가 늘어날 수 있다.
- 여러 도메인을 함께 변경하는 트랜잭션 흐름을 이해하고 구현하는 비용이 커진다.
- 이벤트를 사용하면 즉시 일관성, 실패 처리, 실행 순서에 대한 추가 정책이 필요하다.

## Decision

현재 프로젝트에서는 **도메인 간 직접 의존을 허용하며, 도메인 경계를 강화하기 위한 공개 인터페이스나 이벤트를 일괄 도입하지 않는다.**

서비스는 유스케이스 구현에 필요한 경우 다른 도메인의 Spring 빈, 저장소, 엔티티 같은 구체 타입에 직접 의존할 수 있다. 패키지 구분은 코드의 책임과 탐색 범위를 나타내지만, 독립 배포 가능한 모듈이나 강제된 접근 경계로 간주하지 않는다.

다만 이 결정은 계층과 도메인 규칙을 없애는 것을 의미하지 않는다. HTTP 계층은 요청 검증과 응답 변환에 집중하고, 여러 도메인을 조율하는 트랜잭션 흐름은 서비스 계층에 둔다. 엔티티 상태는 필드를 외부에서 직접 변경하지 않고 해당 엔티티가 제공하는 메서드로 변경하여 불변조건을 보존한다.

## Consequences

- 결제 완료처럼 여러 도메인에 걸친 흐름을 하나의 서비스와 트랜잭션에서 명시적으로 조율할 수 있다.
- 다른 도메인의 타입에 대한 컴파일 타임 결합과 변경 전파를 수용한다.
- 단순히 도메인이 다르다는 이유만으로 중계 서비스, 공개 인터페이스, 도메인 이벤트를 추가하지 않는다.
- 순환 의존은 허용하지 않으며, 새 의존이 생길 때는 유스케이스를 소유한 서비스가 조율 책임을 갖는지 검토한다.
- 외부 시스템이 추가되는 경우에는 이 결정과 별개로 공급자 SDK와 도메인 사이에 명시적인 포트와 어댑터 경계를 둔다.

## Reconsider When

다음 중 하나가 발생하면 도메인별 공개 인터페이스, 모듈 경계 또는 이벤트 기반 통합 도입을 다시 검토한다.

- 도메인 간 순환 의존이 발생하거나 의존 방향을 지속적으로 통제하기 어려워진다.
- 한 도메인의 내부 변경이 여러 도메인에 반복적으로 큰 수정 또는 장애를 유발한다.
- 도메인별 독립 테스트, 병렬 개발, 배포 또는 별도 서비스 분리가 필요해진다.
- 하나의 트랜잭션과 데이터베이스로 도메인 간 일관성을 유지할 수 없게 된다.
- 접근 가능한 타입과 공개 계약을 도구나 빌드 단계에서 강제할 필요가 생긴다.
